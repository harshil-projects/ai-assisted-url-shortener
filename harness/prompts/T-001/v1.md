# Prompt v1: T-001 build gates and CI

Reconstructed record, see `harness/prompts/T-000/v1.md` for why T-000 and T-001 carry
after-the-fact prompt files. Executed in the same interactive session as T-000, immediately after
the first green compile.

## Instruction given

Using `docs/design/2026-10-12-system-design.md` section 4.1 (gates), 4.5 (CI) and 2.2 (tool
versions):

1. Derive `config/checkstyle/checkstyle.xml` from the `google_checks.xml` shipped with Checkstyle
   14.3.0 and add the project rules: `MethodLength` 50 with empty lines not counted, `FileLength`
   400, a multi-line regex that rejects `@Autowired` on fields, and `AbbreviationAsWordInName`
   relaxed to two capitals so `*IT` test names pass. Mark every addition with a `PROJECT` comment.
2. Write `config/checkstyle/suppressions.xml` so Javadoc presence rules apply only to the `api`
   package and tests are exempt from `MethodLength`, each with its reason.
3. Write `config/spotbugs/exclude.xml` with one reasoned entry per exclusion and nothing else.
4. Wire the gates in the poms: Spotless check at `validate`, Checkstyle at `verify` with
   `violationSeverity=warning` and test sources included, SpotBugs with FindSecBugs at effort max
   and threshold medium, JaCoCo `check` with the thresholds from NFR-09 and a class-level rule that
   no production class is left entirely untested, the enforcer ranges, the Mockito agent on the
   Surefire `argLine` chained with `@{argLine}`, and the opt-in `perf` profile.
5. Write the CI workflow (verify on Ubuntu with `-Pperf` and on Windows, report upload with
   `if: always()`, gitleaks history scan, release job on `v*` tags) and the Dependabot config.
6. Prove each gate fails for the right reason before accepting it.

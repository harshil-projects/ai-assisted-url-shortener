## Normalized problem statement

Not yet normalized. The sentence does not say which dimension "where" means, who consumes the answer, over what time window, or whether storing anything about the visitor is acceptable. The design deliberately does not pre-decide it. T-201 records dated questions, dated answers, the candidate directions with cost and privacy implications, and the decision; this section is rewritten there. The constraint already fixed is the privacy posture of ADR 0006: no IP addresses and no raw user-agent strings are persisted.

## Functional requirements covered

- FR-15: outcome determined by T-201 and recorded here; T-202 implements it, T-203 tests and documents it.

## Non-functional requirements covered

- NFR-06 privacy: binds any direction that touches IP or user agent.
- NFR-03 reliability: any attribution value must be captured on the request thread into the immutable event; nothing may delay the redirect beyond a queue offer.
- NFR-10 change safety: if a migration is needed it is V3, single-column `ALTER` statements only.
- NFR-02 performance: the redirect path stays one indexed read plus a queue offer.

## Decision (T-201, 2026-10-12T08:10:00+05:30)

| Field | Decision |
|---|---|
| Dimension | Referring site (host of the `Referer` header) and campaign (`utm_source`, `utm_medium`, `utm_campaign` on the short link request) |
| Consumption surface | `GET /api/v1/links/{code}/stats` gains `referrers` and `campaigns`, each at most ten rows ordered by clicks descending |
| Time window | All clicks of the link; the existing 24-hour and 7-day totals are unchanged; a window parameter is a follow-up |
| Storage change | Migration V3 adds four nullable columns to `click_events`, one `ALTER TABLE ... ADD COLUMN` per column; T-202 is therefore high impact with reason schema |
| Privacy position | Unchanged: no IP, no user agent, no geography, no device, no full referrer URL; values are bounded (host 253, campaign fields 64) and control characters are removed |
| Redirect behaviour | Unchanged; query parameters on the short link are recorded, not forwarded to the destination |

Candidates weighed:

| Candidate | Storage need | Privacy position (ADR 0006) | Cost | Outcome |
|---|---|---|---|---|
| Referring site (host only) | one nullable column | compatible; host of the previous page, no identifier | low | chosen |
| Campaign parameters on the short link request | three nullable columns | compatible; marketing-authored labels | low | chosen |
| Geography from IP | IP or a GeoIP lookup at request time | incompatible; IP is personal data | medium, needs a GeoIP database | removed from scope |
| Device or browser family | user agent string or a parsed family | incompatible as designed; raw UA is personal data when combined | medium | removed from scope |
| Time of day | none, derivable from `occurred_at` | compatible | low | deferred; derivable later from existing data |
| Query parameter forwarding to the destination | none | n/a | medium; needs an open-redirect analysis of appending untrusted query strings | deferred, documented |

Normalized criteria for T-202 are recorded in `harness/tasks/T-202.yaml` as FR-15a to FR-15e.

## Assumptions

- No real marketing team exists; the dated question-before-answer record is the evidence of clarification (#1.4).
- At least one answer removes scope, otherwise the clarification did no work.
- Any direction that stores a value derived from IP or user agent needs an ADR amending 0006 before T-202.

## Out of scope

- Provisional until T-201 decides: raw IP or raw user-agent storage; third-party analytics services; real-time dashboards.
- Server-side fetching of destination pages to infer anything.

## Tasks

T-201 normalization and decision; T-202 implementation of the decided slice, high impact if it adds V3; T-203 tests, docs, decision record update.

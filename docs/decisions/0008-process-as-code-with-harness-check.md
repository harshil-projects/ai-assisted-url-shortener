# Process as code: YAML task specs and ledger validated by JUnit tests in a separate module, raw AI output captured before review

In the context of proving disciplined AI-assisted execution to reviewers who will clone and build, facing the need for traceability that can be checked rather than narrated, we decided for YAML task specs and a YAML ledger validated by JUnit tests in a separate `harness-check` module, with raw AI output snapshotted before review, and neglected Markdown-only process evidence, a mini platform, and JSON Schema files, to achieve checkable traceability that runs inside `mvnw verify` without touching product code, accepting that the harness validates presence, consistency, and computed kept ratios but not the quality of a rationale.

## Context and Problem Statement

The assignment brief asks for task specs, disciplined prompting, traceability of generated, edited, and rejected output, quality gates, secure AI usage, and human sign-off. Narrative evidence can be written after the fact in one voice with uniform timestamps. How is the process recorded so that a reviewer can check it with the same command that checks the product?

## Decision Drivers

| Driver | Weight |
|---|---|
| Evidence checkable by a build, not only readable | High |
| Raw AI output preserved before the engineer edits it | High |
| Product code untouched by process tooling | High |
| Portable: YAML, Markdown, one small Java module, two scripts | High |
| Fits the timebox, about 300 lines of Java | High |

## Considered Options

1. YAML specs and ledger, JUnit validator module, raw patches, PowerShell capture scripts
2. Markdown-only process evidence
3. A mini platform with a database and a web view
4. JSON Schema files for the YAML, validated by nothing in the build

## Decision Outcome

Chosen option 1. `harness/` holds the engineering system as data: requirements, task specs, prompt versions, raw AI patches, gate logs, the ledger, review artifacts, playbooks, and the policy. `harness-check` is a Maven module whose JUnit tests read `harness/`, the source tree, and git history when available; each failure names the violated rule (HC-01 to HC-12) and the offending file, and the module writes `traceability.md` to its `target/` directory. `scripts/snap.ps1` captures the raw AI diff before any edit, `scripts/gate.ps1` appends gate records with real timestamps and log paths, and `scripts/report.ps1` copies the report to `docs/reports/`. The kept ratio per file is computed from the raw patch against the committed diff; the status and rationale are engineer-asserted and labelled so in the report.

### Consequences

| Kind | Consequence |
|---|---|
| Good | `mvnw verify` fails on a missing prompt, patch, log, ledger entry, or sign-off |
| Good | Timestamps and logs are written by scripts, so backfilling from memory is visible |
| Good | Rejections and edits with rationale become the strongest evidence of judgment |
| Good | Product module carries no process dependency |
| Bad | The harness cannot judge whether a rationale is honest or a review was careful |
| Bad | Capture adds about eight minutes per task |
| Bad | Git-history rule skips with a notice when no `.git` or `baseline` tag exists |

### Confirmation

| Check | Where defined |
|---|---|
| `harness-check` JUnit tests report zero violations in the default build | NFR-11, process traceability gate in section 4.1 |
| HC-07 validates the `Task:` trailer against git history when present | Section 5.8 |
| `docs/reports/traceability.md` is deterministic, no timestamps, regenerated by `scripts/report.ps1` | Section 5.2 |

## Pros and Cons of the Options

| Option | Pros | Cons |
|---|---|---|
| YAML, JUnit module, raw patches, scripts | Checkable in the build; portable; small | Presence and consistency only; capture overhead |
| Markdown only | Fastest to write | Unverifiable; easy to backfill; one voice |
| Mini platform | Rich views and queries | Days of work; a new runtime for reviewers; distracts from the product |
| JSON Schema files | Formal shape | Nothing in the build validates them; a liability that drifts |
